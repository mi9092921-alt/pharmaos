## الأعراف الملزمة (تُطبَّق في كل معلم)

كل معلم يلتزم أعراف Phase 0–2 نفسها (تُبقي CI أخضر)، زائد أعراف التحليلات:

1. **الهجرات:** `supabase/migrations/` فقط، تسلسل يبدأ `…002500` تصاعدياً؛ down مقترن؛ كل جدول جديد بالأعمدة الإلزامية + `branch_id` (تشغيلي) + `trg_*_touch`؛ الحالات `VARCHAR + CHECK`؛ لا تعديل مباشر لـ `/supabase`.
2. **التقارير للقراءة فقط:** كل تجميع في SQL (لا N+1، لا حساب ثقيل بالعميل)؛ كل تقرير يأخذ `branch_id` + مدى تواريخ؛ التواريخ باليوم المحلي للفرع (كنمط تقرير Z)؛ ترقيم ≤100 لأي قائمة صفوف.
3. **الأداء (معيار قبول):** تقرير يومي < ٣ث؛ `EXPLAIN ANALYZE` لأي استعلام > 50ms؛ فهارس تغطية للمسارات الساخنة + حرّاس خطة استعلام (`test_query_plans.py`) لكل فهرس جديد.
4. **RBAC:** الصلاحيات من `permissions.ts` فقط؛ `reports.*` قائمة تُستخدَم كما هي؛ `alerts.*`/`notifications.*` تُضاف append-only ويُعاد توليد البذرة (CI يفحص الطزاجة).
5. **الأخطاء/التدقيق:** أكواد جديدة (إن لزمت) تُضاف لـ `errors.ts`+`errors.py`+i18n؛ استخدم ثوابت `AuditAction` القائمة — أي فعل تدقيق جديد يجب أن يكون ضمن السجل المغلق (لا اختراع؛ إن لزم، يُعرض كقرار).
6. **الرسوم البيانية:** Recharts (حسب مكدس CLAUDE) على لوحة الويب؛ الخادم يُعيد التجميعات، والعميل يرسم؛ أي تبعية JS جديدة تُثبَّت بقفل مُلتزَم.
7. **الواجهة:** RTL أولاً، Zustand + TanStack Query، مكوّنات `@pharmaos/ui`، لا `alert/confirm`، أرقام `tabular-nums` وتنسيق EGP، سلاسل ar+en مع كل شاشة، الحماية بـ `hasPermission` (والفحص الخلفي هو الحاسم).
8. **التنبيهات/الإشعارات لا تعطّل المسارات الأساسية أبداً:** توليدها idempotent ومُزال التكرار؛ الفشل يُسجَّل ولا يوقف بيعاً/استلاماً.
9. **قنوات لا تُدَّعى بلا مزوّد:** الإشعار داخل التطبيق/سطح المكتب في Phase 3؛ البريد خلف بوابة مزوّد مُهيّأ (نمط محوّل الامتثال) والقبول «بانتظار المزوّد»؛ SMS مؤجَّل لـ Phase 4.
10. **الاختبارات + التنسيق:** لكل معلم خدمة + HTTP (مصفوفة صلاحيات + CSRF للتحويلات) على PostgreSQL حقيقي؛ الحزمة كلها خضراء؛ prettier/ruff/black/mypy؛ commit `feat(scope): …` + Co-Authored-By؛ الدفع عبر تكامل GitHub (عدا `.github/**`).

## تفصيل المعالم — التقارير (P3-M1 … P3-M5)

### P3-M1 — أساس التقارير + تقارير المبيعات

- **الهدف:** طبقة تقارير + راوتر + لوحة /reports مع رسوم Recharts؛ مبيعات يومي/شهري/سنوي.
- **الهجرة 2500 (إن لزمت):** فهارس تغطية للتجميع الزمني (`invoices(branch_id, created_at)` قائم كـ `idx_invoices_date` — قد يكفي؛ أضف فهرس `payments(cash_session_id)`/`(branch_id,created_at)` عند اللزوم فقط بعد EXPLAIN).
- **الملفات:** `services/reporting_service.py` (تعميم `day_report` لمدى تواريخ: إجمالي/صافي المبيعات، المرتجعات، بطريقة الدفع، أعلى الأصناف، اتجاه زمني)؛ `routers/reports.py` (`reports.sales`/`reports.financial`؛ تصدير CSV بـ `reports.export`)؛ `apps/web/.../reports/` (لوحة + Recharts) + `nav.ts` (`ready:true`) + `api.ts` + i18n.
- **قرار D1 (Recharts):** إضافة التبعية + قفل مُلتزَم. **قرار D2 (استراتيجية الحساب).**
- **التحقق:** صحة التجميعات مقابل مبيعات مُهيّأة؛ **تقرير يومي < ٣ث** (حارس أداء/خطة استعلام)؛ صلاحيات + CSV.

### P3-M2 — تقارير المخزون

- **الهدف:** مستوى المخزون (مع حد إعادة الطلب)، تحليل الحركة (`stock_movements` بالنوع/المدة)، تقييم المخزون (قيمة الدفعات النشطة)، وبطيء/سريع الحركة.
- **الملفات:** توسيع `inventory_service` (تقارير) + `reports.py`؛ يعيد استخدام `batch_status_report`. فهرس على `stock_movements(branch_id, movement_type, created_at)` عند اللزوم.
- **التحقق:** دقة الحركة/التقييم؛ صلاحية `reports.inventory`.

### P3-M3 — تحليلات الانتهاء والهدر

- **الهدف:** دلاء ٣٠/٦٠/٩٠ (يعيد استخدام `expiry_alerts`) + **قيمة الإهلاك** (`stock_movements` type=`expiry_writeoff`) + اتجاه القرب من الانتهاء + قيمة المحجوز.
- **الملفات:** توسيع `inventory_service`/`reporting_service` + الواجهة (بطاقات + رسم).
- **التحقق:** مطابقة القيم للدلاء والكنس؛ قراءات فقط.

### P3-M4 — تحليل الأرباح والخسائر

- **الهدف:** الإيراد الصافي (`invoice.subtotal`)، **تكلفة البضاعة المباعة COGS = Σ(`invoice_item.qty_smallest` × `batch.purchase_price`)** عبر `invoice_item.batch_id`، هامش إجمالي لكل صنف/فئة/مدة، ثم صافي تشغيلي = الهامش − المصروفات.
- **قرار D3 (أساس COGS).** أثقل معلم تحليلي.
- **الملفات:** `reporting_service` (استعلامات ربحية) + `routers/reports.py` (`reports.financial`/`finance.reports`) + لوحة الربحية.
- **التحقق:** مثال محسوب يدوياً (شراء/بيع/هامش)؛ استبعاد المرتجعات؛ الأداء.

### P3-M5 — أداء الموردين + تحليلات العملاء

- **الهدف:** الموردون (عدد/قيمة أوامر الشراء، زمن الاعتماد→الاستلام، نسبة التوريد الكامل)؛ العملاء (الأعلى إنفاقاً، سجل الشراء، أرصدة الولاء، RFM مبسّط).
- **الملفات:** `reporting_service` (يعيد استخدام `customer_history` + `purchase_orders` + `payments`) + الواجهة.
- **التحقق:** دقة المجاميع؛ صلاحيات.

## تفصيل المعالم — التنبيهات والإشعارات والتقسية (P3-M6 … P3-M8)

### P3-M6 — محرّك التنبيهات الذكي

- **الهدف:** تقييم `ALERT_RULES` (CLAUDE.md): مخزون منخفض (≤ reorder_point)، نفاد (=0)، انتهاء حرِج/تحذير (٣٠/٩٠)، خصم يتجاوز حد الفرع (`max_discount_percent`)، فرق صندوق (عند الإغلاق)، تراكم إيصالات ETA > ٢٤ث، فشل تتبّع EDA > ٣ محاولات، فشل مزامنة، نسخ احتياطي متأخر > ٢٤ث، انحراف مخزون.
- **الهجرة 2600:** `alerts` (branch_id، rule_key، severity، entity_type/id، message_key + params JSONB، status: active|acknowledged|resolved، dedup_key فريد للنشِط، first_seen/last_seen، acknowledged_by/at) + إلزامية + down. **صلاحيات جديدة `alerts.view`/`alerts.manage` (append-only).**
- **الملفات:** `services/alerts_service.py` (مقيّمو القواعد + توليد idempotent مُزال التكرار عبر dedup_key + إقرار/حل)؛ نقطة توليد على الإقلاع + CLI + `POST /alerts/evaluate` (على غرار expiry-sweep)؛ `routers/alerts.py`؛ بانر لوحة + شاشة تنبيهات. **قرار D4 (تخزين).** **قرار D6 (مُطلِق).**
- **التدقيق:** إعادة استخدام أفعال قائمة فقط؛ لا فعل جديد بلا قرار.
- **التحقق:** كل قاعدة تُطلِق حالتها؛ تكرار التوليد لا يضاعف الصفوف (dedup)؛ الإقرار يعمل؛ صلاحيات + CSRF.

### P3-M7 — نظام الإشعارات

- **الهدف:** تسليم داخل التطبيق + سطح المكتب؛ مركز إشعارات؛ موصول بالتنبيهات + أحداث مفتاحية (نسخ متأخر، فرق صندوق). البريد **خلف بوابة مزوّد مُهيّأ** (لا يُدَّعى تسليم بلا SMTP)؛ SMS مؤجَّل.
- **الهجرة 2700:** `notifications` (user_id/branch_id، channel: in_app|desktop|email، priority: low|medium|high|critical، title/body_key + params، read_at، sent_at، related_alert_id nullable) + إلزامية + down. **صلاحيات `notifications.view`/`notifications.manage` (append-only).**
- **الملفات:** `services/notification_service.py` (إنشاء + وسم مقروء + بوابة قناة البريد)؛ `routers/notifications.py` (قائمة/وسم مقروء/عدّاد غير المقروء)؛ مكوّن جرس + مركز إشعارات في الويب (استطلاع دوري عبر TanStack Query). **قرار D5 (نطاق القنوات).**
- **التحقق:** إنشاء من تنبيه؛ عدّاد غير المقروء؛ وسم مقروء؛ البريد no-op بلا مزوّد؛ صلاحيات + CSRF.

### P3-M8 — تقسية + حصاد القبول + توثيق

- **الهدف:** تشغيل معايير قبول Phase 3 من طرف لطرف؛ حرّاس أداء (**تقرير يومي < ٣ث**)؛ بوابة OWASP؛ `docs/phase3-acceptance.md` (كل معيار → التنفيذ + الاختبار) + تحديث README ووثيقة المشروع؛ تلميع اللوحات (حالات فارغة، تحميل، RTL).
- **التحقق:** الحزمة كاملة خضراء + كل الهجرات up/down/re-up + الأداء موثَّق.

## قرارات مطلوبة قبل البدء

أوقفت التنفيذ لحسم التالي (خيارات + توصية) — أحتاج قرارك قبل كتابة أي كود:

- **D1 — رسوم Recharts:** إضافة `recharts` (مكدس CLAUDE) كتبعية جديدة + قفل مُلتزَم (npm صار متاحاً محلياً). **توصيتي:** نعم — Recharts هو الخيار المعتمد في المواصفة. (البديل: رسم SVG داخلي بلا تبعية — أبطأ تطويراً.)
- **D2 — استراتيجية حساب التقارير:** تجميع SQL عند الطلب مقابل جداول لقطات مُجدوَلة. **توصيتي:** تجميع SQL عند الطلب + فهارس تغطية (حجوم جهاز واحد متواضعة)؛ إدخال لقطات/تخزين مؤقت فقط إذا تجاوز تقرير هدف < ٣ث.
- **D3 — أساس تكلفة الأرباح (COGS):** **توصيتي:** تكلفة الدفعة FEFO وقت البيع (`invoice_item.batch_id` → `batch.purchase_price`) — لا تكلفة محمَّلة منفصلة. (يطابق «الدفعات مصدر الحقيقة».)
- **D4 — تخزين التنبيهات:** جدول `alerts` مخصّص (توليد بقاعدة + dedup + إقرار) يغذّي `notifications` (تسليم) — مقابل دمجهما. **توصيتي:** الفصل (alerts للحالة، notifications للتسليم) — أوضح وأقابل للتوسّع.
- **D5 — نطاق قنوات الإشعار:** **توصيتي:** داخل التطبيق + سطح المكتب في Phase 3؛ البريد خلف بوابة مزوّد مُهيّأ (القبول «بانتظار المزوّد»، نمط محوّل الامتثال)؛ SMS مؤجَّل لـ Phase 4.
- **D6 — مُطلِق توليد التنبيهات:** **توصيتي:** عند الطلب (endpoint) + على الإقلاع + CLI (كنمط `expiry-sweep`)؛ عامل مجدوَل (Celery beat) بند بنية تحتية لاحق لا يحجب Phase 3.
- **D7 — أفعال تدقيق/إشعار جديدة:** سجل التدقيق مغلق في CLAUDE.md. **توصيتي:** لا فعل تدقيق جديد لـ alerts/notifications (ليست في السجل)؛ إن رغبت بتدقيقها لاحقاً يُعرض كتعديل صريح للسجل. الإشعارات نفسها ليست سجل تدقيق.

## المخاطر ومعايير القبول وقيود البيئة

**المخاطر:**

- **أداء التقارير على جهاز واحد (Docker PG):** التخفيف = تجميع SQL + فهارس + حارس «< ٣ث» على التقرير اليومي؛ EXPLAIN لأي > 50ms.
- **تضخّم نطاق التحليلات (تنويعات لا نهائية):** التخفيف = مجموعة MVP من بنود المواصفة السبعة فقط؛ تأجيل الإضافات لـ backlog.
- **ضجيج التنبيهات:** التخفيف = dedup عبر dedup_key + شدّة + إقرار/حل + عتبات من `ALERT_RULES`.
- **غياب مزوّد بريد/SMS:** التخفيف = بوابة مزوّد (نمط الامتثال)؛ لا ادعاء تسليم؛ القبول «بانتظار المزوّد».
- **تبعية JS جديدة (Recharts) + القفل:** لمرة واحدة؛ npm متاح محلياً الآن؛ يُلتزَم `pnpm-lock.yaml`.
- **لا مُجدوِل (Celery beat) موصول:** توليد التنبيهات عند الطلب/الإقلاع/CLI؛ الجدولة بند تشغيلي لاحق.

**معايير القبول (نصاً من المواصفة) ومطابقتها:** تقرير يومي < ٣ث ← M1/M8 (حارس أداء)؛ إطلاق التنبيهات وفق القواعد ← M6؛ تسليم الإشعارات (داخل التطبيق/سطح المكتب؛ البريد بانتظار المزوّد) ← M7.
