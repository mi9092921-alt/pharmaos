# الخطة والقرار الموحدان: فحص التداخلات الدوائية وإرشاد سلامة الدواء

- **الحالة:** خطة وقرار موحدان للتنفيذ المرحلي؛ لا تعني أن الميزة جاهزة للإطلاق.
- **التاريخ:** 2026-11-01
- **المصدر الوحيد لوثائق الميزة:** هذا الملف.
- **أصل البيانات التنفيذي:** [drug-interactions-seed.sql](data/drug-interactions-seed.sql) — ليس وثيقة سردية، ولا يُعتمد إنتاجيًا قبل بوابات هذه الخطة.
- **نطاق الخطة:** DDI-M1 إلى DDI-M7، ثم خطة `Medication Counseling / Patient Safety Notes` وبوابة الإطلاق.
- **قاعدة حاكمة:** لا كتابة على قاعدة `pharmaos`، ولا تعديل على `drug-interactions-seed.sql` قبل إغلاق DDI-M1 ومراجعة أدلته؛ تحديثات القرار تُسجل هنا فقط.

يستبدل هذا الملف الوثائق السردية المتعددة الخاصة بالميزة. لا تُنشأ وثيقة أخرى لشرح DDI أو Counseling؛ تُضاف القرارات والتحديثات إلى هذا الملف. يبقى ملف SQL منفصلًا لأنه artifact بيانات/تنفيذ يحتاجه الاختبار والهجرة.

## 1. الهدف وحدود النطاق

الهدف هو بناء فحص تداخلات محلي، قابل للتدقيق، يعمل دون شبكة في مسار نقطة البيع، ويعامل نقص التعرف أو نقص التغطية كحالة غير آمنة معرفيًا، لا كدليل على عدم وجود تداخل.

لا تشمل هذه الخطة:

- OCR أو LLM أو أي استدعاء سحابي في مسار البيع.
- ربط تلقائي للأدوية بالمواد الفعالة اعتمادًا على التشابه النصي فقط.
- حجب نهائي للبيع؛ القرار النهائي للصيدلي أو المسار الاستثنائي المصرح به.
- تعديل الهجرات الموجودة؛ أي تغيير مخطط يضاف كهجرة جديدة ومعها `down` واختبار up/down.

## 2. خط الأساس قبل التنفيذ

يجب تسجيل هذه القيم في أول تقرير M1، ولا تُعتبر افتراضات ثابتة حتى تثبتها البيئة:

- عدد الهجرات الموجودة: **36**.
- عدد ملفات `down`: **36**.
- نسخة PostgreSQL: **17** محليًا.
- ملف البيانات المرجعي الحالي: `docs/data/drug-interactions-seed.sql`، وهو ليس هجرة نشطة.
- قاعدة البيانات التشغيلية: `pharmaos` فقط؛ قواعد الاختبار والنسخ المؤقتة تستخدم أسماء حرفية منفصلة.

قبل البدء يجب التأكد من عدم وجود تغييرات غير مقصودة في شجرة العمل. الملفات غير المرتبطة بهذه الميزة تُحفظ كما هي ولا تُنظف أو تُعاد كتابتها.

## 3. قرار مصادر البيانات للأوفلاين

لا يوجد مصدر مجاني واحد يحقق في الوقت نفسه تغطية كاملة، تحديثًا مستمرًا، ترخيصًا تجاريًا واضحًا، وبيانات DDI منظمة جاهزة للإدخال. لذلك يعتمد PharmaOS طبقات منفصلة:

| الطبقة                    | المصدر المعتمد                           | الوظيفة                                                             | القرار                                                                          |
| ------------------------- | ---------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| الدليل السريري للتداخل    | DailyMed / FDA Structured Product Labels | استخراج Section 7 والتفاصيل المرتبطة بالآلية والإدارة               | المصدر الأساسي للإنتاج بعد تنزيل snapshot محلي ومراجعة صيدلي                    |
| هوية المادة والمنتج       | RxNorm/RxNav محليًا + EDA مصر            | ربط الاسم التجاري بالمادة الفعالة و`ingredient_id` وRxCUI عند توفره | هوية فقط، وليس مصدر DDI                                                         |
| تغطية ومقارنة إضافية      | DrugCentral                              | مصدر مرشح لاكتشاف بيانات أو نصوص إضافية                             | لا يدخل الإنتاج قبل إثبات schema وprovenance والترخيص في DDI-M3                 |
| اختبار ومقارنة غير تجارية | DDInter 2.0                              | كشف الفجوات واختبارات regression                                    | ممنوع توزيعه داخل منتج تجاري؛ ترخيصه CC BY-NC-SA 4.0 وآخر تحديث معلن 2024-05-14 |
| مجموعة أمان صغيرة         | ONC high-priority DDI set                | regression set للتداخلات الخطيرة                                    | ليست مصدر تحديث ولا قاعدة تغطية                                                 |

### 3.1 طريقة التشغيل الأوفلاين

لا يستدعي POS أي API خارجي. تتم عملية التحديث خارج مسار البيع:

```text
DailyMed/FDA snapshot + EDA/RxNorm identity files
        ↓
تدقيق hash ونسخة المصدر
        ↓
استخراج وتطبيع ومراجعة صيدلي
        ↓
قاعدة DDI محلية داخل PostgreSQL
        ↓
POS يعمل محليًا دون شبكة
```

DailyMed يوفر ملفات SPL وواجهات لاسترجاع النشرات الحالية وتنزيلات دورية. يعتمد الاستخراج على Section 7، مع حفظ `set_id` وتاريخ النسخة والرابط. لا تعني غياب فقرة أو زوج في النشرة أن التداخل غير موجود.

### 3.2 عقد provenance الإلزامي

لا يدخل أي زوج إلى dataset إنتاجي دون:

```text
source_dataset
source_version
source_url
source_document_id
source_section
source_published_at
evidence_type
reviewed_by
reviewed_at
```

القيم الممكنة لـ`evidence_type` تشمل `label`, `regulatory`, `literature`, `curated`, و`cross_check`. أما `source = fda_label` وحدها فلا تكفي؛ يجب حفظ الوثيقة والقسم والتاريخ.

### 3.3 تصحيح وضع المصادر القديمة

- `drug-interactions-seed.sql` بيانات starter أولية، لا مصدرًا سريريًا نهائيًا. صفوفه الحالية تحتوي `fda_label` و`onchigh` و`literature` كتصنيفات عامة، وستحتاج provenance ومراجعة صيدلي قبل التبني.
- DrugCentral متاح بتنزيل قاعدة حديث في 2026، لكن صفحة التنزيل لا تثبت وحدها أن جدول DDI المقترح مناسب للإنتاج؛ لذلك يبقى مرشحًا حتى DDI-M3.
- DDInter 2.0 ليس “All Rights Reserved” فقط؛ شروطه الرسمية `CC BY-NC-SA 4.0`، ولذلك يستخدم للتحقق الداخلي غير التجاري فقط.
- RxNav لم يعد يقدم DDI API؛ يستخدم RxNorm/RxClass للهوية والتصنيف فقط.

الروابط المرجعية الرسمية:

- [DailyMed SPL resources](https://dailymed.nlm.nih.gov/dailymed/spl-resources.cfm)
- [FDA prescribing information — Section 7](https://www.fda.gov/drugs/fdas-labeling-resources-human-prescription-drugs/prescribing-information-resources)
- [RxNav APIs](https://lhncbc-portal.lhcaws-prod-pub.nlm.nih.gov/RxNav/APIs/index.html)
- [EDA drug database description](https://www.edaegypt.gov.eg/media/ajqiccqc/np-ppma-18-mechanism-of-egyptian-drug-database-eddb-searching-tool.pdf)
- [DrugCentral download](https://www.drugcentral.org/download) و[license](https://www.drugcentral.org/privacy)
- [DDInter statistics](https://ddinter2.scbdd.com/statistics/) و[terms](https://ddinter2.scbdd.com/terms/)

### 3.4 الأولويات غير القابلة للتنازل

1. دقة تحديد المادة الفعالة قبل أي مطابقة.
2. مصدر موثق لكل علاقة دوائية.
3. فصل شدة التداخل عن قوة الدليل.
4. عدم اعتبار غياب البيانات دليلًا على السلامة.
5. عدم حجب البيع تلقائيًا؛ النظام ينبه ويسجل وقرار الصرف للصيدلي.
6. تسجيل ما عُرض وما قرره المستخدم بصورة قابلة للمراجعة.
7. تحديث البيانات بإصدارات وتقارير فرق دون إفساد النسخ السابقة.
8. تنفيذ الفحص دون إنترنت داخل قاعدة محلية.

## 4. العقود المقفلة قبل كتابة الكود

### 4.1 عقد نتيجة الفحص

يعيد الفحص كائنًا بهذه الحقول، مع إبقاء القائمتين منفصلتين:

```text
{
  check_completed,
  has_interactions,
  all_ingredients_identified,
  alerts[],
  unidentified[],
  identified_no_pairs_in_dataset[],
  dataset_scope: {
    source,
    version,
    ingredients_count,
    pairs_count,
    scope: "basket_only"
  },
  check_hash
}
```

`basket_only` إلزامية في العقد والواجهة والدليل. لا يجوز عرض عبارة تعني “آمن” عندما تكون مادة غير معروفة أو عندما تكون التغطية غير مكتملة.

### 4.2 التمثيل المعياري و`check_hash`

يُحسب الهاش من JSON UTF-8 معياري، بالمواصفات التالية:

1. المفاتيح مرتبة ترتيبًا معجميًا، ولا توجد مسافات زائدة.
2. معرّفات UUID بحروف صغيرة.
3. الكميات تمثل كنص عشري معياري، لا كـ floating point.
4. عناصر السلة ترتب بـ `(medication_id, packaging_id, quantity)`.
5. يتضمن المدخل `branch_id` ونسخة dataset ونسخة العقد، حتى لا تتطابق نتيجة قديمة مع سياق مختلف.
6. الناتج SHA-256 بحروف hex صغيرة.

يُعاد حساب الهاش داخل معاملة `create_sale` بعد بناء السلة النهائية وقبل خصم المخزون. تغيير الكمية أو التعبئة أو المادة يبطل الإقرار القديم ويرجع `E-DDI-002` أو `E-DDI-004` بحسب موضع الفشل.

### 4.3 المراجعة والهوية

- هوية المطابقة الوحيدة هي `ingredient_id` الداخلي.
- `key` النصي يستخدم للمطابقة غير المرجعية/العرض فقط.
- `external_id_status` منفصل عن `link_status`.
- الأزواج تطبع عند الإدخال إلى `(a < b)` حسب `(entity_type, entity_id)`، مع السماح صراحةً بـ `(G,G)`.
- الشدة الأعلى هي الشدة المعروضة دائمًا؛ النص التفسيري الأخص هو المستخدم عند وجود أكثر من مصدر.
- جدول `ddi_reviews` يستخدم قيدًا فريدًا على:

```text
(branch_id, session_user_id, fingerprint_kind, fingerprint)
```

إعادة استخدام `review_id` مسموحة لنفس المستخدم والفرع والنوع والبصمة فقط، ولا تُعتمد على الجلسة وحدها.

### 4.4 عقد الإقرار والتوكن

التوكن الخام لا يُخزّن. يُخزّن `token_hash` فقط. التوكن:

- عشوائي 256-bit، أحادي الاستخدام، وTTL مدته 10 دقائق.
- مرتبط بـ `review_id` و`fingerprint` و`fingerprint_kind` و`decisions[]`.
- `fingerprint_kind` إما `full_check` أو `basket_only`.
- `kind` إما `alerts_ack` أو `check_skipped`.
- `issued_by` هو المقرر، و`session_user_id` هو صاحب جلسة البيع.
- لا يصدر توكن `check_skipped` إذا كان فحص حديث ناجح يعرض تنبيهات لم تُقر.

يتم الاستهلاك داخل معاملة البيع بتحديث شرطي ذري من نوع:

```sql
UPDATE ddi_ack_tokens
SET consumed_invoice_id = :invoice_id, consumed_at = now()
WHERE token_hash = :token_hash
  AND consumed_at IS NULL
  AND expires_at > now()
RETURNING ...;
```

يجب أن يكون عدد الصفوف المتأثرة واحدًا. مشغل قاعدة البيانات يمنع أي انتقال غير `NULL → قيمة`، وقيد فريد على `consumed_invoice_id` يمنع ربط فاتورة واحدة بتوكنين. فشل البيع يتراجع معه الاستهلاك ويبقى التوكن صالحًا حتى انتهاء TTL.

### 4.5 مصفوفة القرار وإعادة المصادقة

| الحالة                                                            | المسار                                                       |
| ----------------------------------------------------------------- | ------------------------------------------------------------ |
| `contraindicated` أو `major`، وصاحب الجلسة يملك `ddi.acknowledge` | إعادة مصادقة بكلمة المرور، والقرارات ترتبط بالتوكن في الخادم |
| `moderate` أو `minor`، وصاحب الجلسة يملك `ddi.acknowledge`        | `POST /pos/ddi-ack` سريع دون كلمة مرور                       |
| `moderate` مع عدم امتلاك الصلاحية                                 | إعادة مصادقة صيدلي/مفوّض                                     |
| `minor` مع عدم امتلاك الصلاحية                                    | عرض فقط؛ لا قرار إقرار                                       |
| شدة `NULL` أو غير مخرطة                                           | تعامل كـ `moderate` على الأقل، ولا تعامل كـ `minor`          |
| فشل تقني في الفحص                                                 | نتيجة `basket_only` مع `E-DDI-004`؛ لا ادعاء بعدم وجود تداخل |

إذا احتوت السلة على `moderate` و`major` معًا، يحدد أعلى مستوى المسار لكل الإقرارات الموجودة، ويرسل كل `decisions[]` في توكن واحد. لا يصدر توكن جزئي.

إعادة المصادقة الذاتية لصاحب الجلسة لا تخضع للسقف العام، لكنها تخضع لقفل `(الحساب المستهدف × المستخدم الطالب)`. المسارات المفوّضة تخضع أيضًا لسقف إجمالي قدره 20 محاولة فاشلة في الساعة لكل حساب مستهدف عبر جميع الطالبين. عند بلوغ السقف:

- يرجع `E-DDI-007 REAUTH_LOCKED` للمسار المفوّض.
- لا يُقفل دخول الصيدلي نفسه.
- يُسمح لمسار طوارئ موثق لمدير الفرع أو `super_admin`، مع تسجيل الحدث وإشعار المدير.

### 4.6 إجراءات التدقيق الستة

تعتمد الميزة هذه القائمة الكاملة، بلا أسماء بديلة:

```text
DDI_ALERTS_SHOWN
DDI_DECISION_RECORDED
DDI_ACK_ISSUED
DDI_REAUTH_FAILED
DDI_ACK_REJECTED
DDI_REAUTH_LOCKED
```

السجل append-only، ويحفظ الفاعل والمفوّض والفرع والبيع/الفاتورة والبصمة ونسخة dataset عند انطباقها.

## 5. قواعد السلامة التشغيلية

ينفذ `run-m1.sh` — عند إنشائه — وفق القواعد التالية:

1. يعزل `DATABASE_URL` و`PGDATABASE` و`PGHOST` و`PGPORT` و`PGUSER` في بدايته، ويمرر الاتصال صراحة لكل أمر.
2. يسمح بإنشاء أو حذف قواعد البيانات من اتصال `postgres` فقط، وباسمي scratch حرفيين فقط:
   `pharmaos_ddi_test` و`pharmaos_backup_verify`.
3. قبل كل عملية وبعد كل ملف seed مطبق، يتحقق من `current_database()`.
4. لا يعدّل `packages/db/scripts/apply-migrations.sh`. تُمسح ملفات الهجرات قراءةً قبل تشغيلها، ثم يُتحقق من قاعدة الاتصال بعد التطبيق. إذا تطلبت بيئة التشغيل تحققًا بعد كل ملف، يطبّق wrapper الملفات واحدًا واحدًا بنفس ترتيبها مع سجل واضح، دون الادعاء بأن ذلك تم عبر السكربت الأصلي.
5. يفشل فورًا عند وجود أي من: `DROP`, `TRUNCATE`, `DELETE`, `UPDATE`, `ALTER`, `GRANT`, `SECURITY DEFINER`, `\c`, `\connect`, `\!`, `\i`, `\ir`, `dblink`, `postgres_fdw`, `COPY ... PROGRAM`.
6. فحص `CREATE EXTENSION` غير الموجود مسبقًا ينطبق على seed فقط؛ الهجرات الأصلية قد تنشئ الامتدادات التي صُممت لها.
7. يثبت `PGCLIENTENCODING=UTF8`، ويحفظ SQL العربي من الملفات كما هو.
8. يمنع أي dump داخل `evidence/`؛ ملفات النسخ تذهب إلى `backups/` فقط، وهي مستثناة من Git.
9. إذا كانت قاعدة scratch موجودة ولا يمكن إثبات أنها قاعدة اختبار تخص الجولة الحالية، يتوقف السكربت ولا يحذفها.
10. لا ينفذ `DROP DATABASE` إلا بعد حفظ الأدلة، وبعد التحقق من أن الاتصال الحالي هو `postgres` وأن الاسم مطابق حرفيًا.

## 6. مراحل التنفيذ والبوابات

### DDI-M1 — إثبات seed والبنية الحالية

**الهدف:** إثبات أن البيانات المرجعية الحالية قابلة للتشغيل والفحص دون لمس `pharmaos`.

#### M1-0: جرد البيئة

المخرجات:

- حالة Docker وPostgreSQL 17 والحاويات والمنافذ.
- جرد الملفات والهجرات والـ downs.
- قراءة `apply-migrations.sh` وتسجيل أنه لا يحمّل `.env` فوق متغير ممرر.
- فحص `.gitignore` ووجود `backups/`.
- التحقق من عدم وجود اتصال نشط بقاعدة الإنتاج قبل أي أمر كتابة.

#### M1-1: نسخة احتياطية قابلة للتحقق

1. تنفيذ `pg_dump -Fc` من داخل حاوية PostgreSQL إلى مسار مؤقت داخل الحاوية.
2. نقل الملف إلى `backups/` عبر `docker cp`.
3. حساب SHA-256 داخل الحاوية وعلى Windows؛ يجب التطابق.
4. إنشاء `pharmaos_backup_verify` فقط من اتصال `postgres`.
5. تشغيل `pg_restore` باستخدام `-d` صريح ومن الملف المنقول.
6. مطابقة أعداد `users`, `permissions`, `medications`, `invoices`, `audit_logs`.

الأدلة: أمر dump، الهاشين، أمر restore، أعداد المقارنة، ونتيجة التحقق.

#### M1-2: قاعدة الاختبار والهجرات

1. إنشاء `pharmaos_ddi_test` من `postgres` فقط.
2. تطبيق الهجرات الـ36 بترتيب الاسم، داخل معاملات لكل ملف وفق مسار المشروع.
3. تطبيق seed RBAC المناسب داخل قاعدة الاختبار.
4. إثبات 36 إصدارًا مطبقًا.
5. إثبات `normalize_arabic('أسبرين') = 'اسبرين'`.

#### M1-3: مسح وتشغيل seed

1. إجراء المسح الميكانيكي قبل التنفيذ.
2. تشغيل seed في معاملة واحدة `psql -1 -f` مع `ON_ERROR_STOP=1`.
3. التحقق من `current_database()` بعد الملف.
4. تسجيل أي عيب في seed دون إصلاحه في هذه المرحلة.

#### M1-4: التحقق البنيوي

تسجل النتائج بأسماء لا بأرقام مجردة:

- `ddi_ingredients`: **105**.
- `ddi_groups`: **19**.
- أعضاء المجموعات: **73**.
- `ddi_pairs`: **88**.

إذا اختلف أي رقم، تفشل البوابة ويُرفق الاستعلام والفرق؛ لا تُعدّل الأرقام لتطابق التقرير.

وتشمل الفحوص:

- أربعة مفاتيح يتيمة على الأقل كما يكشفها الاستعلام، مع قائمة الأزواج المتأثرة.
- التكرارات، الأزواج المعكوسة، والأزواج الذاتية غير المتوقعة = صفر.
- `severity` و`source` مكتملان 100%.
- `key = normalize_arabic(key)` لكل الصفوف.
- عدم وجود صفوف ميتة أو أعضاء مجموعات بلا مادة.

#### M1-5: مصفوفة الدوال

تُنفذ داخل قاعدة الاختبار، وتشمل:

1. زوجين معروفين بشدتين مختلفتين.
2. زوج بلا سجل.
3. مادة غير معروفة بالاستبطان.
4. الزوج المعكوس.
5. دواء مركب بمادتين.
6. سلة من خمسة أدوية = عشرة أزواج فريدة.
7. أسماء تجارية تُحل إلى المواد عبر مسار الهوية المعتمد.
8. اختبار حالة العيب `warfarin + NSAID = 0` إذا كان ذلك هو العقد المعتمد للنسخة الحالية.
9. إثبات أن الشدة مأخوذة من صف البيانات لا من قيمة ثابتة في الدالة.
10. مسار `by_ids` داخل `ROLLBACK`، مع إثبات عدم بقاء أي صف.

#### M1-6: Idempotency

تشغيل seed مرة ثانية، ثم مقارنة:

- أعداد جميع الجداول.
- MD5 أو hash لمخرجات استعلامات مرتبة حتميًا.
- عدم وجود صفوف مكررة أو تحديثات صامتة.

#### M1-7: مراجعة أمان SQL

لكل دالة DDI موجودة:

- إخراج `pg_get_functiondef`.
- إثبات `SECURITY INVOKER` و`search_path=public` عند انطباقهما.
- مراجعة `prosecdef` و`proconfig`.
- إثبات أن المنح للمالك فقط، ولا توجد صلاحية حذف/تعديل غير لازمة.

#### M1-8: التقرير والبوابة

المخرجات:

```text
evidence/ddi-seed-validation-2026-11-01/report-ar.md
evidence/ddi-seed-validation-2026-11-01/001-*.txt
evidence/ddi-seed-validation-2026-11-01/002-*.txt
...
```

يحتوي التقرير على ستة أحكام قبول: العزل، سلامة النسخة، نجاح الهجرات، سلامة seed، اكتمال الفحوص، وidempotency/الأمان.

لا تُغلق M1 إلا بعد مراجعة التقرير واعتماد قائمة الإصلاحات، وعلى رأسها المفاتيح الأربعة اليتيمة إن ظهرت.

### DDI-M2 — مخطط DDI التشغيلي

بعد اعتماد M1 والعقود فقط:

- إضافة هجرات جديدة مصنفة، ولكل هجرة `down` واختبار up/down.
- رفع `SUPPORTED_SCHEMA_VERSION` بعد تثبيت الرأس النهائي فقط.
- إنشاء طبقة `ddi_ingredients` النهائية، و`medication_ingredients` بحالات `suggested → pending_review → approved`.
- إنشاء المجموعات والأعضاء والأزواج بالعقد الكامل، مع `(G,G)`.
- إنشاء `ddi_override_reasons`.
- إنشاء `ddi_reviews` و`ddi_ack_tokens` كجداول تشغيلية تحمل `branch_id NOT NULL`.
- فصل `ddi_pairs_ref` المرجعي الخارجي عن جدول التشغيل.
- تحويل الدوال إلى `SECURITY INVOKER` مع `SET search_path=public`.
- إنشاء طابور اقتراحات الربط مرتبًا بالمبيعات، وعدم احتساب الاقتراح قبل `approved`.

البوابة: `verify-up-down.sh` أخضر، مراجعة المالك، وعدم وجود تعديل على الهجرات السابقة.

### DDI-M3 — بوابة مصدر البيانات

قبل استيراد أي صف خارجي إلى dataset الإنتاج:

1. اعتماد مسار DailyMed/FDA كالمسار الأساسي: تنزيل snapshot، تحقق hash، استخراج Section 7، وتجربة على مجموعة مواد محددة.
2. إثبات بنية جدول التداخلات الفعلية داخل DrugCentral إن أريد استخدامه كمصدر إضافي.
3. إثبات جدول الشدة ومصدر قيمه وآلية ربط INN لكل مصدر.
4. استخراج مستقل دون RDKit في مسار البيع؛ لا يُسمح بتحميل قاعدة خارجية أثناء الفحص.
5. حفظ ملف الترخيص وprovenance والإصدار والتاريخ.
6. قرار Go/No-Go موثق لكل مصدر؛ عند No-Go يتوقف استيراده ولا يُبنى افتراض على مصدر غير مثبت.

### DDI-M4 — الإصدارات والدمج

- إنشاء `ddi_dataset_versions` و`ddi_pairs_ref` منفصلين.
- حفظ تقرير diff: جديد، معدّل، مفقود.
- الربط عبر `inn_en` المؤكد فقط.
- إبقاء الاستيراد خارج الهجرات.
- عدم استخدام `ON CONFLICT DO NOTHING` لإخفاء تحديثات المصدر.
- اختبار اختلاف الشدة بين إصدارين مع حفظ التاريخ السابق.

### DDI-M5 — الخدمة ومسار البيع

المخرجات:

- `ddi_service.py`.
- `POST /pos/ddi-check`.
- `POST /pos/ddi-ack` للمسار السريع.
- `POST /auth/re-verify` للمسار المصرح، مع CSRF والقفل والسقف والإشعار.
- تعشيق واحد داخل `create_sale`: فحص → تحقق من الهاش/الإقرار → أقفال FEFO → خصم → استهلاك التوكن داخل نفس المعاملة.
- أخطاء `E-DDI-001..007`.
- إجراءات التدقيق الستة.
- أوفلاين فعلي بحجب socket خارج localhost.

اختبار الأداء: استعلام الفحص أقل من 50ms مرتين، وP95 لمسار الفحص أقل من 200ms على بيئة القياس المسجلة.

### DDI-M6 — الواجهة

إنشاء `DdiConfirmModal` يعرض:

- الشدة والآلية من البيانات.
- المصدر والإصدار و`dataset_scope` و`basket_only`.
- قرارًا لكل تنبيه وفق المصفوفة.
- `reason_code` إلزاميًا لكل `major` و`contraindicated`.
- إلغاء واضح، focus management، وحارس `keydown`.
- لافتة سطرية لكل مادة غير معروفة.
- لافتة `CHECK_FAILED`.
- وسم: «بيانات مستوردة لم تُراجع سريريًا» حتى اعتمادها.
- القاموسين العربي والإنجليزي واختبار `check:i18n`.

لا تُعرض واجهة DDI للمستخدم قبل إغلاق M1–M5.

### DDI-M7 — التحقق الشامل والتسليم

يجب أن تغطي الاختبارات:

- الإقرار، إعادة الاستخدام، السباق بتوكن واحد، وانتهاء TTL.
- فشل البيع وبقاء التوكن صالحًا.
- تغيير الكمية أو البصمة ورفضه.
- mismatch في `kind` أو `fingerprint_kind`.
- إعادة المصادقة والقفل والسقف ومسار الطوارئ.
- الإلغاء والبيع في المسار الوحيد.
- الشدة المجهولة → `moderate`.
- مطابقة `decisions[]` كاملة: لا نقص ولا زيادة ولا تكرار.
- الأوفلاين، P95، وهدف 50ms.
- الصفوف الستة للتدقيق مع الفاعل والمفوّض.

ثم تنفذ:

```text
pytest
check:i18n
typecheck
lint
verify-up-down.sh
```

وتُجرى جلسة POS يدوية موثقة: تنبيه `major`، إعادة مصادقة، قرارات مرتبطة بالتوكن، مبرر مرمّز، إتمام البيع، توكن مستهلك مرتبط بالفاتورة، وسجل تدقيق كامل.

## 7. خطة Medication Counseling / Patient Safety Notes

هذه الخطة جزء من نفس المنتج والوثيقة، لكنها ليست جزءًا من محرك DDI ولا من قرار الإقرار. هدفها عرض معلومات دوائية عملية ومصدرية للمريض أو الصيدلي، مثل الآثار المتوقعة، طريقة الاستخدام، المتابعة، وعلامات الخطر.

### MC-1 — نطاق الملاحظات وتصنيفها

لكل ملاحظة نوع واحد على الأقل من الأنواع التالية:

```text
expected_effect      أثر متوقع غالبًا
administration       طريقة الاستخدام أو التناول
monitoring           فحوص أو متابعة مطلوبة
red_flag             علامة تستلزم تواصلًا طبيًا
handling              التخزين أو التعامل أو التحذير من التلوث
```

لا تستخدم الملاحظة كلمة “آمن” أو “طبيعي” بشكل مطلق. الصياغة تكون احتمالية ومحددة، وتفصل بين الأثر المتوقع وعلامة الخطر.

### MC-2 — نموذج البيانات

تنشأ جداول Counseling كجداول كتالوج مرجعية بلا `branch_id`:

```text
medication_safety_notes
  id, ingredient_id, note_type, message_ar, message_en,
  priority, is_active, created_at, updated_at

medication_safety_note_sources
  note_id, source_dataset, source_version, source_url,
  source_document_id, source_section, source_published_at,
  reviewed_by, reviewed_at, evidence_type
```

الملاحظة لا تُقبل إذا لم يكن لها مصدر ووضع مراجعة. لا يُستخدم LLM لتوليد معلومة طبية؛ يمكن استخدامه فقط لتبسيط نص وافق عليه المصدر والمراجع الصيدلي.

### MC-3 — هرم المصادر

1. النشرة المحلية أو بيانات EDA عند توفرها.
2. DailyMed/FDA للنشرة الرسمية والـ patient counseling.
3. MedlinePlus لتبسيط لغة المريض، وليس كمصدر سريري مستقل عن النشرة.
4. مراجعة صيدلي معتمد قبل النشر.

كل snapshot يحمل hash وتاريخًا، وتبقى النسخة التي عُرضت للمريض قابلة للتتبع.

### MC-4 — مثال إلزامي للصياغة الآمنة

بالنسبة للريفامبين، لا تكتب الواجهة «البول سيكون دمويًا». الصياغة المقترحة:

> قد يتحول لون البول والعرق والدموع أو اللعاب إلى برتقالي أو أحمر برتقالي أثناء استخدام ريفامبين، وهذا أثر متوقع للدواء. إذا بدا البول دمويًا فعلًا، أو ظهر بول داكن جدًا مع اصفرار العينين/الجلد أو ألم بالبطن، تواصل مع الطبيب فورًا.

يجب أن تحفظ الملاحظة رابط النشرة وقسمها وإصدارها. اللون المتوقع لا يلغي احتمالات مرضية أخرى، ولا يقوم النظام بتشخيصها.

### MC-5 — الواجهة والتجربة

تظهر الملاحظات عند اختيار الدواء أو قبل إتمام البيع، مع فصل بصري واضح:

- **أثر متوقع غالبًا:** معلومات غير حاجبة.
- **طريقة الاستخدام:** تعليمات عملية.
- **متى تطلب المساعدة:** تنبيه واضح، دون تشخيص.
- **تداخلات دوائية:** تظل بطاقة DDI مستقلة تمامًا.

لا تدخل ملاحظة Counseling في `check_hash` أو `decisions[]` الخاصة بالتداخلات، إلا إذا كان هناك قرار منتج منفصل موثق بذلك.

### MC-6 — اختبارات القبول

- كل ملاحظة تظهر بالمصدر والإصدار المناسبين.
- لا تُعرض ملاحظة غير مراجعة على أنها حقيقة نهائية.
- اختلاف اللون المتوقع عن “وجود دم” واضح في النص.
- الملاحظة لا تطمس علامة خطر مرتبطة بنفس الدواء.
- العمل دون شبكة بعد تثبيت snapshot المحلي.
- اختبار العربية والإنجليزية، وسهولة القراءة على POS.
- audit اختياري لعرض الملاحظة، دون خلطه بإجراءات DDI الستة.

## 8. بوابة الإطلاق

لا يتم الإطلاق إلا بعد:

1. اعتماد صيدلي موثق (`reviewed_by`) للأزواج التي ستظهر في المنتج.
2. اعتماد `severity_mapping_version`.
3. مراجعة أزواج `major` و`contraindicated` التي تمس الأصناف الأكثر بيعًا خلال آخر 90 يومًا. إذا لم يوجد سجل كافٍ، يحدد الصيدلي قائمة احتياطية موثقة.
4. تعريف نسبة الضوضاء المقبولة وتوثيقها: أسطر البيع المرتبطة والمعتمدة أو الموسومة صراحةً «لا مادة فعالة/غير منطبق».
5. تقرير تغطية الكتالوج.
6. وسم كل بيانات غير مراجعة سريريًا.

أي فشل في شرط الإطلاق يؤدي إلى إيقاف مؤقت، لا إلى حجب دائم ولا إلى ادعاء سلامة.

## 9. شكل الأدلة وقواعد التسليم

كل مرحلة تضع أدلتها في مجلدها دون أسرار أو كلمات مرور أو توكنات خام. كل ملف دليل يبدأ بـ:

```text
stage: DDI-Mx
timestamp: 2026-11-01T...+02:00
database: <scratch name or redacted>
command: <redacted if sensitive>
result: PASS|FAIL
```

عند الفشل، يُحفظ أول خطأ ومخرجاته وتُوقف المرحلة. لا يُعاد تشغيل الخطوة فوق الفشل دون تسجيل سبب الإعادة. لا يُوسم commit أو milestone باسم DDI-Mx قبل وجود تقريره ومراجعة البوابة الخاصة به.

## 10. ترتيب الاعتماد النهائي

```text
DDI-M1
  → مراجعة الأدلة واعتماد الإصلاحات والعقود
DDI-M2
  → DDI-M3 Go/No-Go
DDI-M4 (فقط عند Go)
  → DDI-M5
  → DDI-M6
  → DDI-M7
  → MC-1 إلى MC-6
  → بوابة الإطلاق
```

المراجعة التالية تكون على تقرير DDI-M1 وأدلته، لا على إعادة صياغة هذه الخطة.
