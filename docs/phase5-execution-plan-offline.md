## الملخص التنفيذي والحالة الموروثة (مُتحقَّق منها)

خطة تنفيذ **المرحلة 5 بنطاق معدَّل بقرار المالك (2026-10-05)**: تشغيل محلي offline بالكامل، **فرع واحد**، **بلا سحابة إطلاقاً**، **تطبيق الجوال مؤجَّل**، وتكاملات التأمين/الدول الأخرى مؤجَّلة. البنود الثقيلة الأصلية في Enterprise (مزامنة سحابية، فروع متعددة، جوال، SAR/AED) تخرج من النطاق وتؤجَّل إلى Phase 6 اللاحقة غير محدَّدة موعدها الآن. **لا سطر كود إنتاجي قبل الموافقة على الخطة + حسم القرارات المفتوحة أدناه.**

**الحالة المُتحقَّق منها على `main` @ `b90762b` (كل CI أخضر):**

- **28 هجرة** (`…000100`→`…002800`)، كلٌّ بـ down مقترن، بوابة up/down/re-up خضراء. **هجرات Phase 5 — إن لزمت — تبدأ من `…003000`** (المتوقع 0–2 هجرة فقط: معظم P5 كود تشغيلي فوق بنية قائمة؛ ملاحظة: هجرة `…002900` موجودة مسبقاً من موجة الترخيص P4-M1).
- **309 اختبار pytest** أخضر على PostgreSQL 17؛ ruff/black/mypy صارم نظيف؛ CI (js/python/migrations) أخضر (P3-M8 + pass مراجعة لاحق).
- Phase 0..3 مكتملة: نقطة بيع offline مُختبَرة (بيع ذرّي FEFO + إيصال ESC/POS + استمرارية عبر إعادة تشغيل PostgreSQL — walking skeleton Phase 0-M12)، كتالوج عربي FTS، مشتريات/دفعات/تسلسلات 2D، مرتجعات/مدفوعات/مصروفات/ض.ق.م، تقارير كاملة، 13 قاعدة تنبيه فعّالة، إشعارات in-app + desktop (+ بريد خلف بوابة مزوّد)، Electron shell يحمّل الواجهة من `127.0.0.1:3000`.

**أساسات جاهزة للاستهلاك (يُعاد استخدامها لا يُعاد بناؤها):**

- `backup_service`: نسخة مشفّرة AES-256-GCM + نسخ مفتاح طوارئ (JWT + مفتاح التشفير) + **تدريب استعادة آلي** في الاختبارات + رابط سحابي NO-OP عمداً بلا تهيئة — **يبقى بلا تهيئة عمداً في هذا النطاق**.
- `alerts_service`: 13 قاعدة منها `backup_overdue` (critical، من نظام الملفات) و`ereceipt_backlog` و`tt_report_failed` و`sync_failed`.
- `compliance/`: `eta_adapter` + `ereceipt_service` (طابور `ereceipt_queue`) و`tt_service` + `eda_tt_adapter` (طابور `tt_events`) بنمط outbox — البيع لا يتوقف على الشبكة أصلاً.
- `docs/pilot-checklist.md`: قائمة فحص جهاز الصيدلية (تثبيت/عتاد/دفق يومي/صمود/نسخ/أمان/تسليم) — أساس التجربة الميدانية في M8.
- **فاحص توازن i18n ar/en** (من P4-M3 — موجة الترخيص): بوابة CI/اختبارات قائمة تُستهلك مباشرة.

**فجوات يجب بناؤها في Phase 5 (معدَّلة):**

- **لا وجهة ثانية للنسخ الاحتياطي** ولا جدولة تلقائية (النسخ اليوم CLI يدوي فقط) — وبلا سحابة تصبح هذه أثقل فجوة تشغيلية.
- **لا صفحة صحة نظام** (حالة DB/مساحة القرص/آخر نسخة/أحجام الطوابير/النسخة الحالية) — الصحة مشتتة بين تنبيهات فقط.
- **تصريف طوابير الامتثال غير انتهازي** (لا backoff تلقائي عند عودة الشبكة ولا إعادة محاولة يدوية من الواجهة — يُتحقَّق ويُقوَّى).
- **لا مثبّت إنتاج/تغليف تشغيلي**: لا إشراف تلقائي على الحاويات مرتَّب الإقلاع، لا tray، لا تدوير سجلات، لا حزمة دعم.
- **لا سياسة دورة حياة للبيانات المتنامية** (audit_log/pack_serials/tt_events) — فاحص i18n صار قائماً من P4-M3.

## الأعراف الملزمة (تُطبَّق في كل معلم)

كل معلم يلتزم أعراف Phase 0–3 نفسها (تُبقي CI أخضر)، زائد أعراف النطاق المعدَّل:

1. **الهجرات:** `supabase/migrations/` فقط، تسلسل يبدأ `…003000` تصاعدياً **عند اللزوم فقط** (معظم المعالم 0 هجرة)؛ down مقترن؛ لا تعديل مباشر لـ `/supabase`.
2. **الصلاحيات:** append-only من `permissions.ts` فقط (المرشَّح الوحيد: `system.health` لصفحة الصحة) + إعادة توليد البذرة (CI يفحص الطزاجة).
3. **التدقيق:** لا أفعال تدقيق جديدة — السجل المغلق في CLAUDE.md يظل مغلقاً؛ صفحة الصحة والنسخ عمليات قراءة/تشغيل.
4. **عقد الـ offline (أهم عرف):** كل ما يُبنى يعمل **بلا شبكة إطلاقاً**؛ أي نداء خارجي يجب أن يكون: **طابور + إعادة محاولة بتراجع + لا يحجب مسار بيع/استلام/طباعة أبداً**؛ أي تبعية جديدة تُفحص ضد الاعتماد الخارجي وقت التشغيل (لا CDN/خطوط بعيدة/licensing phone-home).
5. **الأداء:** تقرير يومي < ٣ث **يُعاد قياسه على عتاد الصيدلية الفعلي** (M6/M8)؛ `EXPLAIN ANALYZE` لأي استعلام > 50ms.
6. **الواجهة:** RTL أولاً، Zustand + TanStack Query، مكوّنات `@pharmaos/ui`، لا `alert/confirm`، `tabular-nums` وتنسيق EGP، سلاسل ar+en لكل شاشة، حماية `hasPermission` والفحص الخلفي حاسم.
7. **التنبيهات/الإشعارات لا تعطّل المسارات الأساسية أبداً** (يستمر كما في P3)؛ القنوات لا تُدَّعى بلا مزوّد.
8. **الاختبارات + التنسيق:** لكل معلم اختبارات على PostgreSQL حقيقي؛ الحزمة كلها خضراء؛ prettier/ruff/black/mypy؛ commit `feat(scope): …` + Co-Authored-By؛ الدفع عبر تكامل GitHub (عدا `.github/**` = لصق يدوي).

## تفصيل المعالم — الأساس التشغيلي (P5-M1 … P5-M4)

### P5-M1 — عقد الـ offline (عزل خارجي كامل + «يوم بلا شبكة»)

- **الهدف:** إثبات رسمي أن النظام كامل الوظائف بلا أي حزمة شبكة خارجة — أن الشبكة تحسّن الامتثال فقط ولا تُشترط لأي مسار تشغيل.
- **المحتوى:** جرد مُعلَن لكل نداء خارجي وقت التشغيل (الخطوط/الرسوم، أي CDN، telemetry، فحوص تحديث، بوابة البريد NO-OP، ETA/EDA عبر الطوابير، رابط النسخ السحابي غير المُهيَّأ، **نظام الترخيص المحلي P4 — تحقق أوفلاين بالتوقيع والمفاتيح المدمجة، بلا أي نداء شبكة**) في وثيقة قصيرة داخل `docs/`؛ سدّ أي تسرّب (استضافة الخطوط محلياً إن وُجد `next/font/google` أو رابط بعيد)؛ **اختبار E2E «يوم بلا شبكة»**: حجب الشبكة على مستوى الحاوية/الجدار الناري ثم تشغيل دفق يوم كامل (دخول → مسح → بيع → طباعة → مرتجع → استلام توريد → تقارير → تنبيهات → نسخة احتياطية) بصفر فشل.
- **التحقق:** الاختبار أخضر على بيئة بلا إنترنت فعلياً (لا mock)؛ الجرد يغطي كل الحزم المشاركة في الإقلاع.
- **نقطة إعادة معايرة:** نتائج الجرد قد تضيف بنود إصلاح صغيرة — تُنفَّذ هنا قبل أي معلم لاحق.

### P5-M2 — النسخ الاحتياطي والتعافي بلا سحابة (أثقل معلم في النطاق)

- **الهدف:** بلا سحابة، النسخ المحلي المتعدد الوجهات + التدريب الدوري هو خط الدفاع الوحيد ضد فقد الجهاز (الخطر الأعلى في سجل المخاطر أصلاً).
- **المحتوى:** **وجهة ثانية قابلة للتهيئة** (`BACKUP_SECONDARY_PATH`: USB/قرص خارجي/مجلد شبكة محلي) تُنسخ إليها النسخة بعد نجاح التشفير؛ **جدولة تلقائية** عبر Windows Task Scheduler (يُنشئها المثبّت في M5، وبإعداد يدوي موثق قبلها) تستدعي أمر CLI القائم + فحص `backup_overdue` يمتد للتحقق من الوجهتين؛ **سياسة احتفاظ** (افتراضي 30 نسخة، الحذف فقط بعد نجاح نسخة جديدة ولا يمسّ الأحدث أبداً)؛ **تنبيه مساحة قرص منخفضة** (قاعدة جديدة `disk_space_low` — عرض كقرار)؛ توسيع تدريب الاستعادة الآلي ليشمل الاستعادة من الوجهة الثانية؛ توثيق سير عمل مفتاح الطوارئ (تصدير USB + دليل ورقي) — **متضمناً مفتاح النسخ الاحتياطي المطلوب لمسار الاستعادة على جهاز نظيف المعرَّف في P4-M2**.
- **الملفات:** توسيع `backup_service` + `alerts_service` + CLI + اختبارات التدريب.
- **التحقق:** drill كامل موثَّق: نسخة → نقل USB → استعادة على قاعدة نظيفة → مطابقة أعداد الصفوف → تسجيله في `docs/phase5-acceptance.md`.

### P5-M3 — الاصطدام والتعافي + صفحة صحة النظام

- **الهدف:** الجهاز الوحيد نقطة فصل واحدة — يجب أن يتعافى النظام ذاتياً من أعطال الوسيط وأن تكون صحته مرئية دائماً (قابل للاستبدال بمعيار المواصفة «حالة المزامنة مرئية دائماً» بهيئته المحلية).
- **المحتوى:** إشراف الحاويات (`restart: unless-stopped` في docker-compose للـ PG/Redis) + **ترتيب إقلاع موثَّق ومُختبر** (DB → API → UI) مع إقلاع تلقائي مع ويندوز؛ **drill: إسقاط PostgreSQL وسط يوم عمل** ثم التعافي بلا فقد حركات (يبني على إثبات M12 القائم ويحوّله اختباراً دورياً)؛ **صفحة `/health`** (صلاحية `system.health` إن أُقرت): حالة DB، مساحة القرص، آخر نسخة احتياطية + وجهتها، أحجام طوابير ETA/EDA المعلّقة، نسخة التطبيق/المخطط؛ **تدوير السجلات** ومستوياتها (ERROR/WARN/INFO) بلا نمو غير محدود.
- **الملفات:** `docker-compose.yml` + `apps/desktop` (انتظار جاهزية الخدمات) + `routers/health.py` + شاشة ويب + `docs/` (دليل أعطال قصير: أعراض → إجراء).
- **التحقق:** drill إسقاط/تعافٍ موثَّق؛ الصحة تعكس الحالات فعلياً (إسقاط يدوي → الحالة تتغير)؛ صلاحيات + CSRF حسب القراءة/التحويل.

### P5-M4 — الامتثال offline-first (تصريف طوابير ETA/EDA)

- **الهدف:** الاتصال اختياري انتهازي: الصيدلية قد تبقى offline أسابيع — لا شيء يُحجب، ولا يضيع إرسال، والطوابير مرئية وقابلة للتصريف اليدوي.
- **المحتوى:** **مُصرِّف انتهازي** يجرّب تصريف `ereceipt_queue`/`tt_events` بتراجع (backoff) عند توفر الشبكة (على إقلاع النظام + عند الطلب) دون تعطيل أي مسار بيع؛ **زر إعادة محاولة يدوي** لكل طابور في شاشة الامتثال القائمة؛ عدادات معلّق/فشل معروضة (تستخدمها `/health` في M3)؛ التحقق من أن قاعدتي `ereceipt_backlog`/`tt_report_failed` تُطلِقان بالعتبات الصحيحة أثناء بقاء offline طويل؛ لا فقد صامت: كل صف طابور إما مُرسَل أو فاشل مع سبب مرئي.
- **الملفات:** `compliance/ereceipt_service.py` + `compliance/tt_service.py` (المُصرِّف) + `routers/compliance.py` + شاشة الامتثال + اختبارات بالمحاكي القائم (شبكة مفقودة → تعود → تصريف كامل).
- **التحقيق:** بالمحاكي: قطع → تراكم → عودة → تصريف بلا فقد ولا تكرار (idempotency)؛ البيع أثناء القطع لا يتأثر أبداً.

## تفصيل المعالم — التشغيل والحصاد (P5-M5 … P5-M8)

### P5-M5 — حزمة التثبيت والتشغيل (packaging)

- **الهدف:** مثبّت واحد على ويندوز نظيف → نظام يعمل كاملاً (يبني على قائمة P1-M11 ويؤتمت أجزاءها) — **ويتكامل مع موجة تغليف الترخيص** (PyInstaller للـ API + bytenode للـ Electron المُعلنة خارج P4) حتى لا يُبنى مثبّتان متنافسان.
- **المحتوى:** مثبّت Electron (NSIS): يشمل shell + متطلبات (Docker Desktop/PG فحص وجود) + إنشاء مهمة Task Scheduler للنسخ (يُنفِّذ قرار M2) + اختصارات؛ **أيقونة tray**: حالة الخدمات/فتح/إيقاف؛ **عرض النسخة الحالية** في الإعدادات + **مسار تحديث عبر USB** (بلا خادم تحديث): مثبّت جديد يُفحص بالتحقق من الإصدار في `docs/versions.md`؛ **حزمة دعم** (support bundle): سجلات + إصدارات + آخر أخطاء → ZIP للمسار الثانوي.
- **قرار D9 (التوقيع):** شهادة توقيع EV/OV (~100–400$/سنة) تُشترى قبل أول توزيع حقيقي؛ قبلها يُسلَّم مثبّت غير موقَّع مع توثيق تجاوز تحذير SmartScreen.
- **التحقق:** تثبيت على ويندوز نظيف (صندوق اختبار) → إقلاع تلقائي → يوم عمل مصغّر → إزالة تثبيت نظيفة.

### P5-M6 — بوابة الأمان والأداء قبل الإنتاج

- **الهدف:** بوابة OWASP Top 10 (شرط الإنتاج في المواصفة) + قياس الأداء على العتاد الحقيقي لا على بيئة التطوير.
- **المحتوى:** قائمة فحص OWASP موثَّقة ومنفَّذة على سطح الهجوم المحلي (headers، rate limits: دخول ٥/د وAPI ٢٠٠/د، RBAC sweep كامل لمصفوفة الصلاحيات عبر كل الراوترات، parameterized، CSRF للتحويلات، إبطال الجلسات عند تغيير كلمة المرور، **بوابة الترخيص P4 ضمن سطح الفحص**)؛ **قياسات العتاد**: تقرير يومي < ٣ث، مسح→إيصال حراري، إقلاع بارد حتى أول عملية بيع، حجوم صفوف واقعية (بذر ضغط: شهور من حركات يومية)؛ مصفوفة الأجهزة (طابعة حرارية/ماسح 2D/درج) وفق `docs/pilot-checklist.md`.
- **التحقق:** تقرير أمان/أداء موثَّق بالأرقام في `docs/phase5-acceptance.md`؛ أي استعلام > 50ms له EXPLAIN وحارس خطة.

### P5-M7 — قفل الفرع الواحد + دورة حياة البيانات + تلميع

- **الهدف:** ترسيخ النطاق المعدَّل في الكود والواجهة، ومعالجة نمو البيانات محلياً.
- **المحتوى:** قفل تطبيقي على الفرع المبذور الوحيد (إخفاء منتقيات الفرع، التحقق الخلفي يرفض إنشاء فرع ثانٍ بصلاحيات عادية — مع إبقاء `branch_id` كامل المخطط)؛ **فاحص توازن i18n ar/en**: **قائم من P4-M3 — يُستهلك وتُوسَّع تغطيته لكل شاشات P5 الجديدة** (لا إعادة بناء)؛ **سياسة دورة حياة**: `audit_log` بلا حذف أبداً (append-only) مع **أرشفة CSV سنوية** للتصدير، مراقبة حجم `pack_serials`/`tt_events`/`stock_movements` (عدادات في `/health`)، جدولة VACUUM/ANALYZE التشغيلية؛ تلميع RTL/حالات فارغة/تحميل عبر الشاشات.
- **التحقق:** الفاحص يفشل عند خلل توازن مقصود؛ أرشفة CSV تُقرأ ويُتحقق من مطابقتها؛ بذرة ضغط لا تكسر أهداف الأداء.

### P5-M8 — حصاد القبول + توثيق + تجربة ميدانية

- **الهدف:** تشغيل معايير قبول هذا النطاق من طرف لطرف + تسليم تشغيلي كامل.
- **المحتوى:** `docs/phase5-acceptance.md` (كل معيار → التنفيذ + الاختبار + الرقم المقيس)؛ تشغيل `docs/pilot-checklist.md` كاملاً على **جهاز الصيدلية الفعلي** (الماسح/الطابعة/الدرج/UPS) مع أسبوع مراقبة؛ **دليل مستخدم عربي** (دفق يومي + أعطال شائعة + النسخ/الاستعادة) + تدريب الطاقم؛ تحديث README و`docs/versions.md` ووثيقة المشروع (progress-and-roadmap)؛ تسجيل إغلاق بندي D2/D5 (بلا سحابة عمداً).
- **التحقق:** الحزمة كاملة خضراء + كل الهجرات up/down/re-up + القبول موثَّق بالأدلة.

## قرارات مطلوبة قبل البدء

أوقفت التنفيذ لحسم التالي (خيارات + توصية) — أحتاج قرارك قبل كتابة أي كود:

- **D1 — وجهة النسخ الاحتياطي الثانية:** مسار محلي مُهيَّأ (`BACKUP_SECONDARY_PATH`) يخدم USB/قرص خارجي/مجلد شبكة محلي بالتساوي. **توصيتي:** كذلك — أوسع تغطية بأقل كود، والفصل الفيزيائي (USB يُرفع مساءً) يُفرض بالإجراء البشري في الدليل. (لا سحابة إطلاقاً؛ رابط Supabase يبقى بلا تهيئة عمداً.)
- **D2 — جدولة النسخ التلقائي:** **توصيتي:** Windows Task Scheduler تستدعي أمر CLI القائم (يعمل حتى لو التطبيق مقفول)؛ البديل — عامل داخل Electron لا ينسخ إلا والتطبيق مفتوح. يُنشئها المثبّت (M5) + إعداد يدوي موثق قبل ذلك.
- **D3 — سياسة الاحتفاظ:** **توصيتي:** 30 نسخة يومية على القرص الداخلي (تنظيف بعد نجاح نسخة جديدة فقط، الأحدث لا يُمسّ أبداً) + أرشفة CSV شهرية يدوية للوجهة الثانية؛ قابلة للتهيئة.
- **D4 — تنبيه مساحة قرص:** قاعدة تنبيه جديدة `disk_space_low` (critical عند العتبة، مثلاً < 10GB) — إضافة على قواعد ALERT القائمة بنفس النمط. **توصيتي:** نعم.
- **D5 — سياسة تصريف الامتثال:** **توصيتي:** تصريف انتهازي تلقائي بتراجع + زر يدوي معاً (التركيز على ألا يضيع إرسال ولا يُحجب بيع)؛ البقاء offline شهوراً مسار مدعوم لا استثناء.
- **D6 — المراقبة/الأخطاء بلا إنترنت:** **توصيتي:** سجلات محلية بمستوياتها + تدوير + صفحة `/health` + حزمة دعم ZIP؛ Sentry (سحابي أو self-hosted) مؤجَّل — يتطلب قناة أو بنية إضافية لا يستحقها فرع واحد.
- **D7 — صلاحية صفحة الصحة:** `system.health` جديدة [super_admin, branch_manager] append-only، أو ربطها بصلاحية إعدادات قائمة. **توصيتي:** جديدة صريحة — أوضح للمراجعة والبذرة.
- **D8 — قفل إنشاء الفروع:** رفض إنشاء فرع ثانٍ (التحقق الخلفي + إخفاء الواجهة) مع إبقاء المخطط كاملاً للتوسع المستقبلي. **توصيتي:** كذلك — القرار الأصلي يبقى قابلاً للعكس بمجرد رفعه.
- **D9 — توقيع المثبّت:** شراء شهادة EV/OV (~100–400$/سنة) قبل أول توزيع حقيقي على الصيدلية؛ أثناء التطوير مثبّت غير موقَّع بتحذير موثَّق. **توصيتي:** نعم عند بلوغ M5 فعلياً.

## المخاطر ومعايير القبول وقيود البيئة

**المخاطر:**

- **فقد الجهاز بلا سحابة (الخطر الأعلى في هذا النطاق):** التخفيف = M2 كاملاً (وجهتان + جدولة + تدريبات استعادة شهرية موثقة + مفتاح طوارئ USB) + UPS ضمن قائمة العتاد.
- **هشاشة PostgreSQL عبر Docker على ويندوز (خطر مسجل أصلاً):** التخفيف = M3 (إشراف + إقلاع مرتّب + drill) ودليل أعطال.
- **انفجار طوابير الامتثال عند بقاء offline طويلاً:** التخفيف = M4 (رؤية + عتبات تنبيه قائمة + تصريف يدوي) — الصفوف لا تُحذف أبداً، لا فقد صامت.
- **اعتماد خارجي متسرَّب يكسر offline:** التخفيف = M1 أولاً (جرد + اختبار شبكة مقطوعة) قبل أي معلم آخر — **يشمل التأكد أن نظام الترخيص P4 لا يضيف أي نداء خارجي**.
- **تضخم نطاق مجدداً (إغراء إعادة إدخال المزامنة/الفروع):** التخفيف = قاعدة MVP — كل بند غير لازم للتشغيل اليومي offline يُؤجل صراحة إلى «مرحلة الاتصال» اللاحقة.
- **أجهزة العتاد متفاوتة:** التخفيف = مصفوفة pilot-checklist على عتاد الصيدلية الفعلي (M6/M8).

**معايير القبول (معدَّلة على النطاق، والموازية من المواصفة الأصلية موضحة):**

1. **يوم عمل كامل والشبكة مقطوعة فعلياً: صفر فشل** في بيع/مرتجع/استلام/تقارير/تنبيهات/نسخ (M1) — البديل المحلي لمعيار «جهازان يتزامنان».
2. **تعافٍ من إسقاط PostgreSQL وسط يوم بلا فقد حركات** (M3) — يوازي «توفيق offline→online كامل» هيئياً.
3. **استعادة كاملة على قاعدة/جهاز نظيف من نسخة الوجهة الثانية + مفتاح الطوارئ فقط** (M2/M8) — يوازي «تعارض مفتعل لا يُحسم صامتاً»: لا فقد صامت في أي مسار (الطوابير إما مرسلة أو فاشلة معلَّلة).
4. **الاتصال اختياري: البيع لا يتوقف بلا إنترنت أبداً، وعند العودة تُصرَّف الطوابير بلا فقد ولا تكرار** (M4).
5. **حالة النظام مرئية دائماً** (صفحة `/health`: DB/مساحة/آخر نسخة/طوابير/إصدار) (M3) — البديل المحلي لـ«حالة المزامنة مرئية دائماً».
6. **تقرير يومي < ٣ث على عتاد الصيدلية الفعلي** (M6/M8) — معيار المواصفة نصاً.
7. **مثبّت واحد على ويندوز نظيف → تشغيل كامل + إقلاع تلقائي** (M5/M8).
8. **CI أخضر دائماً + كل الهجرات up/down/re-up + تغطية ≥ 80% لمنطق الأعمال الجديد** (كل المعالم).

**نقاط إعادة المعايرة:** بعد M1 (نتائج الجرد/الاختبار قد تضيف بنود)؛ بعد M2 (أول drill حقيقي — اضبط الاحتفاظ/العتبات)؛ عند M5 (قرار توقيع D9 قبل التوزيع)؛ قبل M8 (جدولة التجربة الميدانية مع مالك الصيدلية).

**قيود بيئة التنفيذ (مؤكَّدة هذا المسار):** جهاز تطوير ويندوز محلي + PostgreSQL 17 (docker-compose) + Python 3.12 عبر uv + npm/pnpm متاحان (بعد فك حظر السجلات)؛ CI على GitHub Actions (js + python + migrations) — الدفع عبر تكامل GitHub عدا `.github/**` (لصق يدوي)؛ وثائق المحادثة تُفقد — كل ما يلزم بقاؤه في المستودع.

**بروتوكول التنفيذ بعد الموافقة:** معلم واحد في كل مرة (اشرح ← نفّذ ← تحقّق بكل البوابات ← commit ← ادفع ← تحقق من CI ← قف وقرِّر التالي)، وتحديث وثيقة المشروع بعد كل معلم.
